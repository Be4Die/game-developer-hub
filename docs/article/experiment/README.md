# Замеры для статьи

`measure.py` измеряет на локальном стенде (`task backend:up`, `task agents:up`, `task stack:seed`) два показателя
для демонстрационной игры № 5 с политикой «масштабирование до нуля»:

- **холодный запуск** — время от запроса обнаружения сервера при отсутствии экземпляров до состояния «Работает»;
- **остановка при простое** — время от готовности экземпляра без игроков до его остановки (тайм-аут простоя 1 мин).

```bash
python3 measure.py results.json cold=20 idle=3
```

Скрипт удаляет созданные им экземпляры и возвращает исходную политику игры. Результаты (`results.json`) читает
`src/build_article.js`: числа в таблице и в аннотации статьи считаются из файла.

## Что выяснилось при замерах (11.11.2026)

1. **Гонка при холодном запуске.** Если запросы обнаружения приходят чаще, чем успевает зарегистрироваться
   запускаемый экземпляр, каждый запрос порождает свой запуск: решение (`DiscoveryService.DiscoverServers`) и
   создание записи об экземпляре (`InstanceService.StartInstance`) не атомарны, повторная проверка предела в
   `autoStartInstance` считает только уже созданные записи. При опросе обнаружения 10 раз в секунду за один
   холодный запуск создавалось до 15–19 экземпляров при пределе 5. Поэтому скрипт отправляет запрос обнаружения
   один раз и дальше опрашивает список экземпляров. Исправление — блокировка запуска по игре (redsync в Valkey).
2. **Принудительно завершённый контейнер не помечается сбойным.** После `docker kill` контейнера экземпляр
   оставался в состоянии «Работает» не менее 60 с (два опыта). Вероятная причина — сверка учитывает и
   завершившиеся контейнеры как существующие на узле. Время восстановления после сбоя поэтому в статье не приводится;
   поведение нужно проверить отдельно.
